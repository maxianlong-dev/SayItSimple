# 大数据技术全景
## 一、大数据技术栈的 6 层架构
数据从产生到被使用，会经过 6 层。**每一层都有对应的工具**。
```markdown
┌─────────────────────────────────────────┐│  6. 应用层：BI 报表、大屏、推荐、风控      │├─────────────────────────────────────────┤│  5. 服务层：把数据快速吐给业务用           │├─────────────────────────────────────────┤│  4. 计算层：算数据（离线 / 实时）          │├─────────────────────────────────────────┤│  3. 存储层：数据放哪里                    │├─────────────────────────────────────────┤│  2. 传输层：数据怎么流过来                 │├─────────────────────────────────────────┤│  1. 采集层：从哪儿搞到数据                 │└─────────────────────────────────────────┘
```
---
## 二、逐层拆解（含代表工具）
### 第 1 层：数据采集（数据从哪来）
**数据源三大类**：
| **类型** | **举例** | **采集工具** |
| --- | --- | --- |
| 业务数据库 | MySQL 订单表 | **Canal / DataX / Flink CDC**（订阅 binlog） |
| 日志文件 | Nginx 日志、App 埋点 | **Flume / Logstash / Filebeat** |
| 外部数据 | 爬虫、第三方 API | 自己写脚本 / 爬虫框架 |
一句话：**Canal 抓数据库变更，Flume 抓日志文件**。
---
### 第 2 层：数据传输（消息队列）
数据采上来后，不能直接写数仓，**要有个"缓冲池"顶住流量高峰**。
| **工具** | **特点** |
| --- | --- |
| **Kafka** | 业界标准，吞吐量巨大，大数据必备 |
| **RocketMQ** | 阿里出的，集团内常用 |
| **Pulsar** | 新一代，云原生 |
一句话：**Kafka 就像一根巨大的传送带，前面塞数据、后面接工人**。
---
### 第 3 层：数据存储（放哪儿）
按用途分四类：
#### ① 业务数据库（OLTP）
处理**实时交易**，要求快、能改。
- **MySQL、PostgreSQL、Oracle**
- **HBase**（分布式 NoSQL，扛得住海量写入）
- **Redis**（内存数据库，缓存用）
#### ② 分布式文件存储
放**原始文件**（日志、图片、Parquet 表格文件）。
- **HDFS**（自建机房）
- **OSS / S3**（云上，逐步取代 HDFS）
#### ③ 数据仓库（OLAP，分析用）
- **离线数仓**：Hive、**ODPS/MaxCompute**（阿里云）
- **实时数仓**：**Hologres**、ClickHouse、Doris、StarRocks
#### ④ 数据湖
"什么都能扔"的架构，底层是 OSS/HDFS，上面加一层**表格式**：
- **Iceberg / Hudi / Delta Lake**（让湖里的文件也能像表一样用）
> 现在流行**"湖仓一体"**：湖的灵活 + 仓的高效，合成一个。
---
### 第 4 层：数据计算（干活的工人）
**核心分两派：离线 vs 实时**
#### ① 离线计算（跑批，T+1）
处理"昨天以前"的历史数据，跑得慢但便宜。
| **工具** | **说明** |
| --- | --- |
| **MapReduce** | 老祖宗，现在没人直接写了 |
| **Hive** | SQL 翻译成 MapReduce，慢 |
| **Spark** | 内存计算，比 Hive 快 10 倍，主流 |
| **ODPS/MaxCompute** | 阿里云托管版，集团标配 |
#### ② 实时计算（流式，秒级）
数据来一条算一条。
| **工具** | **说明** |
| --- | --- |
| **Storm** | 老古董 |
| **Spark Streaming** | 微批，伪实时 |
| **Flink** | 真·流处理，业界标准 |
#### ③ OLAP 即席查询（交互式秒查）
不是跑批，是"用户点一下立刻出结果"。
| **工具** | **场景** |
| --- | --- |
| **Presto / Trino** | 跨源联邦查询 |
| **ClickHouse** | 单表巨快，报表神器 |
| **Doris / StarRocks** | 国产新秀，实时报表 |
| **Hologres** | 阿里云，Flink 最佳搭档 |
---
### 第 5 层：数据服务（把数据吐给业务）
数据算完了，得让业务系统能查。
- **数据 API 网关**：包一层 HTTP 接口给前端
- **指标平台**：统一口径，"GMV"全公司只有一个定义
- **Redis / HBase**：把结果缓存起来，扛高并发
---
### 第 6 层：数据应用（终点）
- **BI 报表**：Tableau、QuickBI、FineBI、Superset
- **实时大屏**：DataV
- **数据科学**：Jupyter + Python + Spark
- **机器学习平台**：PAI、MLflow
- **推荐/风控/画像**：直接调用数据服务
---
## 三、贯穿全流程的 3 个"辅助系统"
除了主链路，还有 3 类**支撑工具**：
### ① 调度系统（管任务什么时候跑）
- **Airflow**（开源主流）
- **DolphinScheduler**（国产）
- **DataWorks**（阿里云）
> 每天凌晨 2 点跑昨天的报表 —— 谁来触发？就是它。
### ② 元数据 / 数据治理
数据多了会乱，需要"数据字典"：
- **Atlas / DataHub / Amundsen**（血缘、字典）
- **Catalog**（表元信息管理）
- **数据质量 DQC**（校验数据对不对）
### ③ 资源管理
- **YARN**（Hadoop 自带的调度）
- **Kubernetes**（云原生，正在取代 YARN）

## 五、两条主链路（记住这两个就够了）
### 🔵 离线链路（T+1 报表）
```plain text
MySQL → DataX → ODPS(Hive) → Spark/SQL 加工 → BI 报表                     ↑              调度：DataWorks 每天凌晨触发
```
### 🔴 实时链路（秒级大屏）
```plain text
MySQL binlog → Kafka → Flink 实时计算 → Hologres → 实时大屏
```
**大部分公司两条都在跑，叫"Lambda 架构"**。
新一点的公司想只跑一条流，叫"Kappa 架构"（Flink + 数据湖）。

## 七、必须知道的数仓分层（面试常问）
数仓内部数据不是一坨堆着，是**分 4 层**加工：
```plain text
ADS  应用层    → 直接给报表用（GMV按天） ↑DWS  汇总层    → 按主题汇总（用户日活） ↑DWD  明细层    → 清洗过的干净明细（每笔订单） ↑ODS  贴源层    → 从业务库原样抄过来 ↑     业务系统 MySQL
```
一句话：**层层加工、越往上越聚合、越贴近业务**。
