# Agent Skill 体系总结
#
## 一、什么是 Agent Skill
Agent Skill 是 AI Agent 系统中的**可插拔能力模块**，为 Agent 提供特定领域的知识和工作流编排能力。
核心定义：**Skill = 领域指令（Prompt） + 触发规则（Trigger） + 工具编排（Orchestration）**
类比理解：
- 如果 Agent 是操作系统，Skill 就是可按需加载的驱动程序
- 如果 Agent 是人，Skill 就是掌握的一项专业技能（如"会做代码审查"）
## 二、解决什么问题
### 核心矛盾
LLM Agent 面临"**能力膨胀**"与"**上下文有限**"的根本矛盾：
- Agent 需要覆盖大量领域（代码审查、数据平台、部署运维、文档协作……）
- 但 Context Window 有限，全部知识塞入会导致注意力稀释和响应质量下降
### Skill 的解法
| 问题 | 解决方式 |
| --- | --- |
| Context Window 膨胀 | 按需加载，未触发的 Skill 不占用上下文 |
| 领域知识冲突 | 每个 Skill 封装独立领域逻辑，互不干扰 |
| 复杂流程难以一次性描述 | 将多步骤操作编排为一个原子化 Skill |
| 系统难以扩展 | 新增能力只需新增 Skill，无需修改核心架构 |
| LLM 自由发挥导致不可控 | 通过明确的触发条件和执行指令约束行为 |
## 三、设计范式
### 3.1 Skill 的三要素
```plain text
┌──────────────────────────────────────┐
│  Trigger    （触发条件）— 何时激活     │
│  Instruction（执行指令）— 做什么怎么做 │
│  Capability （依赖能力）— 用什么完成   │
└──────────────────────────────────────┘
```
### 3.2 触发机制
```plain text
触发方式
├── 显式触发：用户通过命令/关键词主动调用
├── 隐式触发：系统根据上下文自动匹配（关键词、链接模式、文件类型等）
└── 优先级仲裁：多 Skill 匹配时按优先级选择
```
**触发条件设计要点：**
- 同时定义"何时使用"和"何时不使用"（正向+负向边界）
- 使用声明式描述，让 Agent 自行判断是否匹配
- 设计互斥规则避免多 Skill 冲突
### 3.3 Skill 分类
按交互模式：
| 类型 | 说明 | 示例 |
| --- | --- | --- |
| 查询型（只读） | 获取信息，不改变状态 | 搜索代码、查询血缘关系 |
| 操作型（写入） | 执行变更操作 | 创建 MR、部署应用 |
| 编排型（多步骤） | 串联多个步骤完成复杂任务 | 深度研究（搜索→抓取→验证→综合） |
| 配置型（元操作） | 修改 Agent 自身行为或配置 | 更新设置、管理权限 |
按领域：
| 类型 | 说明 | 示例 |
| --- | --- | --- |
| 平台集成类 | 对接外部平台 API | CI/CD、项目管理、数据平台 |
| 代码工程类 | 围绕代码生命周期 | 审查、测试、重构、安全扫描 |
| 知识研究类 | 信息检索与综合 | 深度研究、文档生成 |
| 运维部署类 | 应用生命周期管理 | 启动、部署、监控 |
### 3.4 核心设计原则
| 原则 | 说明 |
| --- | --- |
| 单一职责 | 一个 Skill 只解决一类问题 |
| 最小权限 | 写操作需用户确认，避免不可逆副作用 |
| 声明式边界 | 通过自然语言描述适用/不适用场景 |
| 渐进复杂度 | 简单场景一步完成，复杂场景支持多轮交互 |
| 幂等可恢复 | 操作可重试，失败不破坏状态 |
| 上下文最小化 | 只注入当前任务需要的指令，不冗余加载 |
## 四、在 Agent 架构中的位置
```plain text
┌─────────────────────────────────────────────┐
│                  用户请求                      │
└─────────────────┬───────────────────────────┘
                  ▼
┌─────────────────────────────────────────────┐
│          Agent Core（推理与决策）              │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐     │
│  │ Planner │  │ Memory  │  │ Router  │     │
│  └─────────┘  └─────────┘  └────┬────┘     │
└──────────────────────────────────┼──────────┘
                                   ▼
┌─────────────────────────────────────────────┐
│            Skill Layer（能力层）               │
│  ┌────────┐ ┌────────┐ ┌────────┐          │
│  │Skill A │ │Skill B │ │Skill C │ ...      │
│  └───┬────┘ └───┬────┘ └───┬────┘          │
└──────┼──────────┼──────────┼────────────────┘
       ▼          ▼          ▼
┌─────────────────────────────────────────────┐
│            Tool Layer（工具层）                │
│  ┌─────┐ ┌──────┐ ┌─────┐ ┌──────┐        │
│  │Read │ │Bash  │ │API  │ │Agent │ ...     │
│  └─────┘ └──────┘ └─────┘ └──────┘        │
└─────────────────────────────────────────────┘
```
**层次关系：**
- **Tool**：原子操作，函数级别（读文件、执行命令、调用 API）
- **Skill**：工作流级别，编排多个 Tool 完成一个领域任务
- **Agent**：决策级别，自主选择调用哪些 Skill/Tool
## 五、与相关概念对比
| 维度 | Skill | Tool（Function Calling） | Agent | Plugin |
| --- | --- | --- | --- | --- |
| 粒度 | 工作流级 | 原子操作级 | 自主决策级 | 应用级 |
| 触发方式 | 规则匹配/命令 | LLM 自行决定 | 显式委派 | 用户安装启用 |
| 上下文开销 | 按需注入 | 函数签名始终可见 | 独立上下文 | 始终加载 |
| 控制权 | Agent 按 Skill 指令执行 | Agent 直接调用 | 子 Agent 自主执行 | 外部系统控制 |
| 可组合性 | 可调用 Tool 和 Agent | 被 Skill/Agent 调用 | 可调用 Skill 和 Tool | 相对独立 |
| 典型实现 | Claude Code Skill、Copilot Skill | OpenAI Function Calling | LangChain Agent | ChatGPT Plugin |
## 六、Skill 的生命周期
```plain text
定义 → 注册 → 触发匹配 → 加载注入 → 执行 → 卸载
```
1. **定义**：编写 Skill 的触发条件、执行指令、依赖声明
2. **注册**：在 Agent 系统中注册，使其可被发现
3. **触发匹配**：用户请求到来时，Router 判断是否匹配某个 Skill
4. **加载注入**：匹配成功后，将 Skill 指令注入当前上下文
5. **执行**：Agent 按照 Skill 指令调用 Tool 完成任务
6. **卸载**：任务完成后释放上下文空间
## 七、设计一个好 Skill 的检查清单
- [ ] 触发条件是否明确？（正向 + 负向边界）
- [ ] 是否满足单一职责？（不混合多个领域）
- [ ] 写操作是否有确认机制？（安全边界）
- [ ] 失败场景是否有兜底？（错误处理/重试）
- [ ] 是否与现有 Skill 存在冲突？（优先级仲裁）
- [ ] 上下文注入量是否合理？（避免占用过多 token）
- [ ] 是否有明确的"不使用"说明？（避免误触发）
## 八、面试话术
### 一句话定义
> "Agent Skill 是 LLM Agent 系统中按需加载的领域能力模块，通过声明式触发规则和结构化执行指令，在不膨胀上下文的前提下为 Agent 提供专业领域的工作流编排能力。"
### 核心价值
> **Context Window 管理** — 按需注入而非全量加载，解决注意力稀释问题**确定性与灵活性的平衡** — 触发条件提供确定性，内部执行保留 LLM 推理灵活性**可组合的分层架构** — Skill 可编排 Tool，也可委派 Sub-Agent，形成 Agent → Skill → Tool 的清晰分层**面向生态的扩展模型** — 类似 IDE 插件体系，第三方可贡献 Skill 而不需理解核心架构
### 与 MCP（Model Context Protocol）的关系
> "MCP 定义了 Agent 与外部工具/资源的通信协议（类似 USB 协议），Skill 则是在此之上的工作流编排层（类似设备驱动）。一个 Skill 可以通过 MCP 协议调用多个外部服务，将其编排为连贯的领域工作流。"
