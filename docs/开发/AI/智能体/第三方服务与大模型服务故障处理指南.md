# 第三方服务与大模型服务故障处理指南
在实际项目中，依赖的第三方服务（尤其是大模型 API）随时可能出现超时、限流、宕机等问题。本文梳理了常见的容错与降级策略，并针对 AI Agent 场景中 Tool 调用异常的处理做了专门补充。
---
## 一、重试机制（Retry）
最基础的容错手段。核心要点是区分可重试错误与不可重试错误：
| 可重试 | 不可重试 |
| --- | --- |
| 超时（Timeout） | 参数错误（400） |
| 服务端错误（5xx） | 认证失败（401/403） |
| 限流（429） | 资源不存在（404） |
### 关键策略
- **指数退避（Exponential Backoff）**：每次重试间隔翻倍，如 1s → 2s → 4s，避免雪崩
- **抖动（Jitter）**：在退避基础上加随机偏移，防止多个客户端同时重试
- **限制重试次数**：一般 2-3 次，避免无限重试拖垮系统
```python
import tenacity

@tenacity.retry(
    stop=tenacity.stop_after_attempt(3),
    wait=tenacity.wait_exponential(multiplier=1, max=10) + tenacity.wait_random(0, 1),
    retry=tenacity.retry_if_exception_type((TimeoutError, ConnectionError)),
)
def call_llm(prompt):
    return client.chat.completions.create(...)
```

## 二、超时控制（Timeout）
大模型服务响应时间波动大，必须设合理的分层超时：
| 超时类型 | 建议值 | 说明 |
| --- | --- | --- |
| 连接超时 | 5-10s | TCP 建连阶段 |
| 读取超时 | 30-120s | 流式输出场景需更长 |
| 端到端超时 | 根据业务设定 | 从用户视角的总超时，防止重试累积耗时过长 |
---
## 三、降级策略（Fallback / Degradation）
当主服务不可用时，按优先级依次尝试备选方案：
```plain text
主模型 → 备用模型 → 缓存结果 → 静态兜底 → 功能降级
```
### 常见降级路径
- **模型降级**：主模型（如 GPT-4）失败，降级到更稳定/便宜的模型（如 GPT-4o-mini）
- **多供应商切换**：OpenAI 不可用时切换到 Anthropic、Azure OpenAI 等
- **缓存兜底**：对相同或相似请求返回缓存结果
- **静态兜底**：返回预设的默认回答，如 "当前服务繁忙，请稍后再试"
- **功能降级**：AI 功能不可用时，退回到规则引擎或人工处理流程
```python
async def get_response(prompt):
    for provider in [call_primary_llm, call_backup_llm, get_cached_response]:
        try:
            return await provider(prompt)
        except ServiceUnavailableError:
            continue
    return DEFAULT_RESPONSE  # 最终兜底
```

## 四、熔断器（Circuit Breaker）
当错误率持续升高时，快速失败而不是继续调用已经不健康的服务。
### 三态模型
```plain text
┌──────────┐  错误率超阈值  ┌──────────┐  超时后探测  ┌──────────┐
│  关闭状态 │ ────────────→ │  打开状态 │ ──────────→ │ 半开状态  │
│ (正常调用) │              │ (快速失败) │             │ (少量探测) │
└──────────┘ ←──────────── └──────────┘             └──────────┘
               探测成功恢复                    失败则重新打开 ↩
```
```python
import pybreaker

breaker = pybreaker.CircuitBreaker(
    fail_max=5,           # 连续失败 5 次触发熔断
    reset_timeout=30,     # 30 秒后进入半开状态
)

@breaker
def call_llm(prompt):
    return client.chat.completions.create(...)
```

## 五、限流与排队（Rate Limiting & Queuing）
大模型 API 普遍有 RPM（每分钟请求数）/ TPM（每分钟 token 数）限制：
- **客户端限流**：用令牌桶/漏桶控制发送速率，避免触发 429
- **请求队列**：高并发时排队处理，削峰填谷
- **优先级队列**：核心业务请求优先，非关键请求可延迟或丢弃
---
## 六、可观测性（Observability）
出了问题得能快速发现和定位：
- 记录每次调用的**延迟、状态码、token 用量、模型版本**
- 设置**告警**：错误率突增、延迟 P99 飙高、token 消耗异常
- **链路追踪**：一个用户请求可能串联多次 LLM 调用，需要 trace ID 串起来
---
## 七、异步化与流式处理
- **异步调用**：不阻塞主流程，用消息队列解耦
- **流式输出（SSE / WebSocket）**：大模型生成慢，流式返回改善用户体感，也能在中途检测到错误时提前中断
- **Webhook 回调**：长耗时任务提交后异步通知结果
---
## 八、典型调用链路
将上述策略串联，一个健壮的第三方服务调用链路如下：
```plain text
客户端限流 → 超时控制 → 熔断器检查 → 调用主模型
                                       ↓ 失败
                                     重试（指数退避）
                                       ↓ 仍失败
                                     降级到备用模型
                                       ↓ 再失败
                                     返回缓存 / 静态兜底
                                       ↓
                                   全程记录指标和日志
```
核心原则：**对外部依赖永远保持不信任态度，假设它随时会挂，设计好每一层的应对方案。**

## 九、Agent 场景：Tool 调用异常的友好处理
在 AI Agent 架构中，LLM 通过 Tool（Function Calling）与外部系统交互。Tool 调用失败是常态而非异常——网络波动、API 限流、参数不合法、权限不足都可能发生。
**直接把原始报错信息抛给用户是糟糕的体验**，更好的做法是将错误信息反馈给 LLM，让 LLM 自行决定如何恢复或如何向用户解释。
### 9.1 问题：直接报错 vs 友好提示
#### 反面示例：直接暴露原始错误
```plain text
用户：帮我查一下北京明天的天气
Agent：调用 weather_api 失败
       Error: HTTPSConnectionPool(host='api.weather.com'):
       Max retries exceeded with url: /v1/forecast?city=beijing
       (Caused by ConnectTimeoutError)
```
用户看到一堆技术细节，既不友好也无法行动。
#### 正面示例：LLM 感知错误后友好回复
```plain text
用户：帮我查一下北京明天的天气
Agent：抱歉，天气服务暂时不可用，我无法获取实时天气数据。
       你可以访问 weather.com 直接查看，或者稍后再问我。
```
### 9.2 核心思路：错误信息回传 LLM 而非直接抛出
关键设计：**Tool 执行失败时，将结构化的错误信息作为 Tool 的返回结果传回给 LLM，由 LLM 决定下一步行动。**
```python
import json
import traceback

def execute_tool_safely(tool_name: str, tool_func, arguments: dict) -> dict:
    """安全执行 Tool，失败时返回结构化错误信息给 LLM"""
    try:
        result = tool_func(**arguments)
        return {
            "role": "tool",
            "tool_call_id": tool_call_id,
            "content": json.dumps(result, ensure_ascii=False),
        }
    except TimeoutError:
        error_msg = (
            f"工具 {tool_name} 调用超时，目标服务可能暂时不可用。"
            f"你可以建议用户稍后再试，或换一种方式回答用户的问题。"
        )
    except PermissionError:
        error_msg = (
            f"工具 {tool_name} 权限不足，当前用户无权执行此操作。"
            f"请告知用户需要相应权限，并建议联系管理员。"
        )
    except ValueError as e:
        error_msg = (
            f"工具 {tool_name} 参数错误：{e}。"
            f"请检查参数后重试，或向用户确认输入信息。"
        )
    except Exception as e:
        error_msg = (
            f"工具 {tool_name} 执行失败：{type(e).__name__}: {e}。"
            f"请根据错误类型决定是否重试，或向用户说明情况并提供替代方案。"
        )

    return {
        "role": "tool",
        "tool_call_id": tool_call_id,
        "content": json.dumps({
            "error": True,
            "error_type": type(e).__name__ if 'e' in dir() else "Unknown",
            "message": error_msg,
        }, ensure_ascii=False),
    }
```
### 9.3 结构化错误信息设计
返回给 LLM 的错误信息应包含足够的上下文，让 LLM 能做出合理判断：
```json
{
    "error": true,
    "error_type": "TimeoutError",
    "tool_name": "search_database",
    "message": "数据库查询超时，目标服务可能暂时不可用。",
    "suggestion": "你可以建议用户缩小查询范围，或稍后再试。",
    "retryable": true,
    "context": {
        "attempted_query": "SELECT * FROM orders WHERE ...",
        "timeout_seconds": 30
    }
}
```
字段说明：
| 字段 | 作用 |
| --- | --- |
| `error` | 标记这是一个错误响应 |
| `error_type` | 错误分类，帮助 LLM 判断严重程度 |
| `message` | 人类可读的错误描述 |
| `suggestion` | 给 LLM 的行动建议 |
| `retryable` | 是否建议重试 |
| `context` | 相关上下文，帮助 LLM 调整参数后重试 |
### 9.4 Agent 框架层面的 Tool 异常处理模式
在 Agent 的主循环中，推荐以下处理流程：
```python
class Agent:
    def run(self, user_message: str):
        messages = [{"role": "user", "content": user_message}]

        for step in range(self.max_steps):
            response = self.llm.chat(messages, tools=self.tools)

            if response.finish_reason == "stop":
                return response.content  # LLM 认为可以直接回复

            for tool_call in response.tool_calls:
                tool_result = self._execute_with_fallback(tool_call)
                messages.append(tool_result)

                # 如果连续失败次数过多，注入系统提示引导 LLM 放弃重试
                if self._consecutive_failures(messages) >= 3:
                    messages.append({
                        "role": "system",
                        "content": (
                            "该工具已连续失败多次，请不要继续重试。"
                            "请直接向用户说明情况，并提供你能给出的最佳建议。"
                        ),
                    })

        # 达到最大步数仍未完成
        return "抱歉，我尝试了多种方式但未能完成你的请求，建议稍后再试。"

    def _execute_with_fallback(self, tool_call) -> dict:
        """带降级的 Tool 执行"""
        tool_name = tool_call.function.name
        arguments = json.loads(tool_call.function.arguments)

        # 第一层：执行主 Tool
        result = execute_tool_safely(tool_name, self.tools[tool_name], arguments)

        # 第二层：如果主 Tool 失败且有备用 Tool，尝试备用
        if result.get("error") and tool_name in self.fallback_tools:
            fallback_result = execute_tool_safely(
                f"{tool_name}_fallback",
                self.fallback_tools[tool_name],
                arguments,
            )
            if not fallback_result.get("error"):
                return fallback_result

        return result
```
### 9.5 System Prompt 中的错误处理引导
在 Agent 的 System Prompt 中明确告知 LLM 如何处理 Tool 错误，是最简单有效的手段：
```plain text
## Tool 调用错误处理规范

当你调用的工具返回错误时，请遵循以下原则：

1. **不要向用户暴露原始错误信息**（如堆栈、状态码、内部 URL）
2. **判断是否可以重试**：
   - 超时、限流类错误：可以换个参数或稍后重试（最多重试 1 次）
   - 参数错误：检查并修正参数后重试
   - 权限、认证错误：不要重试，直接告知用户
3. **判断是否有替代方案**：
   - 如果有其他工具可以达成同样目的，尝试使用替代工具
   - 如果你自身的知识可以部分回答，先提供已知信息
4. **友好告知用户**：
   - 用通俗语言解释发生了什么
   - 给出明确的下一步建议（稍后再试 / 换个方式提问 / 手动操作路径）
   - 不要说"系统错误"、"内部异常"等技术术语
5. **保持透明但不过度**：
   - 告诉用户你"无法获取实时数据"比"一切正常"更值得信赖
   - 但不需要解释 TCP 连接池耗尽的细节
```
### 9.6 不同错误类型的 LLM 回复示例
| 错误类型 | LLM 应如何回复 |
| --- | --- |
| Tool 超时 | "查询服务响应较慢，我先根据已有信息回答你，如需最新数据可以稍后再问我。" |
| Tool 限流（429） | "当前请求较多，我稍后帮你重试。" （Agent 自动延迟重试） |
| 参数解析失败 | "我需要更多信息来完成查询，请问你能补充一下 XX 吗？" |
| 权限不足 | "这个操作需要额外权限，你可以联系管理员开通 XX 权限后再试。" |
| 服务不可用（5xx） | "相关服务暂时不可用，你可以稍后再试，或者我先用已知信息帮你分析。" |
| 返回数据为空 | "没有找到相关结果，你可以试试调整查询条件，比如 XX。" |
| Tool 返回格式异常 | "获取到的数据格式有误，我换一种方式帮你查询。" （自动 fallback） |
### 9.7 完整示例：带错误处理的 Agent 对话流
```plain text
用户：帮我查一下订单 ORD-12345 的物流状态

Agent 内部：
  → 调用 tool: query_logistics(order_id="ORD-12345")
  → 返回: {"error": true, "error_type": "TimeoutError", "retryable": true, ...}
  → LLM 决定重试一次
  → 调用 tool: query_logistics(order_id="ORD-12345")
  → 返回: {"error": true, "error_type": "ServiceUnavailable", ...}
  → LLM 决定尝试备用方案
  → 调用 tool: query_order_detail(order_id="ORD-12345")
  → 返回: {"status": "shipped", "carrier": "SF Express", "last_update": "2024-01-15"}

Agent 回复：
  物流服务暂时查询不到实时轨迹，但根据订单信息，你的订单 ORD-12345
  已通过顺丰速运发出，最后更新时间是 1 月 15 日。
  如需查看详细物流轨迹，可以到顺丰官网用运单号查询，或稍后再问我。
```

## 总结
| 层次 | 策略 | 适用场景 |
| --- | --- | --- |
| 网络层 | 超时控制、重试、熔断 | 所有外部调用 |
| 服务层 | 降级、多供应商切换、缓存 | 大模型 / 第三方 API |
| 应用层 | 限流、排队、异步化 | 高并发场景 |
| 可观测 | 日志、指标、链路追踪、告警 | 全链路 |
| Agent 层 | 错误回传 LLM、System Prompt 引导、连续失败熔断 | AI Agent / Tool Calling |
**Agent 场景的核心原则：Tool 的错误是给 LLM 看的，不是给用户看的。让 LLM 作为"翻译层"，把技术异常转化为用户可理解、可行动的自然语言回复。**
