# 消息队列（Message Queue）知识梳理
## 一句话定义
消息队列是一个**中间人**——生产者把消息丢进去，消费者从里面取出来处理。两边互不等待，互不感知。
```plain text
Producer  ──→  [ Queue ]  ──→  Consumer
  发消息         暂存/路由        收消息并处理
```
## 解决什么问题
| 场景 | 没有MQ | 有MQ |
| --- | --- | --- |
| **异步** | A调B，A要等B做完才能返回 | A丢消息就返回，B慢慢处理 |
| **解耦** | A直接调B的接口，B挂了A也挂 | A只管发消息，B挂了消息还在队列里 |
| **削峰** | 1万请求同时打到服务，直接崩 | 消息堆在队列里，消费者按自己的速度消费 |
实际场景举例：
- **RabbitMQ + AI视频**：典型的**异步+削峰**。视频生成很慢，请求先入队，worker 按算力慢慢消费，用户不用干等。
- **RocketMQ + 回调触发**：典型的**解耦+事件驱动**。上游发消息，下游订阅后触发回调逻辑，上下游互不依赖。
## 核心概念
```plain text
                        Exchange / Topic
                        (路由规则)
                            │
Producer ──→ Message ──→ ┌──┴──┐ ──→ Consumer Group A
                         │Queue│ ──→ Consumer Group B
                         └─────┘
```
- **Producer**：发消息的一方
- **Consumer**：收消息的一方
- **Topic / Exchange**：消息的分类/路由规则（"这条消息该去哪"）
- **Queue**：实际存放消息的地方
- **Consumer Group**：同组内的消费者竞争消费（一条消息只被组内一个人消费），不同组各消费一份（广播效果）
- **ACK**：消费者告诉MQ"我处理完了"，MQ才删消息。没ACK的消息会重新投递（保证不丢）
## RabbitMQ vs RocketMQ 对比
| 维度 | RabbitMQ | RocketMQ |
| --- | --- | --- |
| **模型** | Exchange + Queue（AMQP协议） | Topic + ConsumerGroup |
| **路由** | 灵活（direct/fanout/topic/headers） | Tag过滤为主 |
| **强项** | 路由灵活、协议标准、社区生态好 | 高吞吐、事务消息、延时消息、顺序消息 |
| **典型场景** | 任务分发、RPC、中小规模异步 | 电商交易、大规模削峰、分布式事务 |
| **语言** | Erlang | Java |
## 通用使用模式
### 1. 点对点（一对一消费）
```plain text
Producer → Queue → 1个Consumer处理
```
任务进队列，worker抢着消费。适合异步任务处理，如AI视频生成。
### 2. 发布/订阅（一对多）
```plain text
Producer → Topic → Consumer A 各收一份
                 → Consumer B 各收一份
```
比如：订单创建后，库存服务、积分服务、通知服务各自订阅处理。
### 3. 延时/定时消息
```plain text
Producer → 延时队列 → 30分钟后投递 → Consumer
```
比如：下单后30分钟未支付自动取消。
### 4. 事务消息（RocketMQ特有）
```plain text
本地事务 + 发消息 绑定成原子操作
```
比如：扣款成功才发"已支付"消息，要么都成功要么都回滚。
## 要注意的坑
- **消息丢失**：开启持久化 + ACK确认机制
- **重复消费**：消费端做幂等（同一条消息处理两次结果一样）
- **消息堆积**：消费能力跟不上时要扩消费者或降级
- **顺序性**：需要严格顺序时要用顺序消息（同一个队列/分区）
## 一句话总结
消息队列的本质就是**用一个中间缓冲区把"发"和"收"拆开**，让系统异步、解耦、扛得住流量。核心思路是一样的，区别在路由模型和附加能力（事务、延时、顺序）上。
