# MySQL 和 Redis 快速理解
---
## 一、MySQL 核心
### 1. 索引与 B+ 树
**口述版**：MySQL 用 B+ 树做索引，因为它矮胖、叶子节点用链表串起来，既能快速定位又能范围扫描。
- **为什么不用二叉树**：太高，每层一次磁盘 IO，高度就是 IO 次数。
- **为什么不用 B 树**：B 树非叶子节点也存数据，一页能放的索引少，树就变高；B+ 树只有叶子存数据，非叶子纯索引，三层就能存两千万行左右。
- **为什么不用哈希**：哈希只能等值查询，不支持范围和排序。
**聚簇索引 vs 二级索引**
- 聚簇索引（主键）：叶子节点存**整行数据**。
- 二级索引：叶子节点存**主键值** → 所以要"回表"再查一次聚簇索引。
- **覆盖索引**：要查的字段索引里都有，不用回表 —— 这是最常用的优化手段。
**最左前缀原则**
> 联合索引 `(a,b,c)` 就像按「省、市、区」排序的通讯录。你知道省可以查，知道省+市可以查，只知道市没法查。
- 遇到**范围查询**后面的字段就用不上索引了（`a=1 and b>2 and c=3`，c 用不上）。
- 索引失效常见坑：字段上做运算/函数、隐式类型转换（字符串字段传数字）、`like '%xx'`、`or` 连接非索引列。
---
### 2. 事务 ACID
**口述版**：A 靠 undo log，D 靠 redo log，I 靠锁 + MVCC，C 是最终目的，由前三个保证。
|  | 含义 | 靠什么实现 |
| --- | --- | --- |
| A 原子性 | 要么全成要么全败 | undo log 回滚 |
| C 一致性 | 数据符合业务规则 | 前三者 + 业务约束 |
| I 隔离性 | 事务之间互不干扰 | 锁 + MVCC |
| D 持久性 | 提交了就不丢 | redo log |
---
### 3. 隔离级别与三大问题
**口述版**：级别越高越安全越慢，MySQL 默认可重复读，而且通过间隙锁基本解决了幻读。
| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | ✅会 | ✅会 | ✅会 |
| 读已提交（Oracle 默认） | ❌ | ✅会 | ✅会 |
| **可重复读（MySQL 默认）** | ❌ | ❌ | 基本解决 |
| 串行化 | ❌ | ❌ | ❌ |
- **脏读**：读到别人没提交的数据。
- **不可重复读**：同一事务两次读**同一行**，值变了（别人 UPDATE 了）。
- **幻读**：同一事务两次读**同一范围**，行数变了（别人 INSERT 了）。
---
### 4. MVCC（高频，必须会讲）
**口述版**：MVCC 就是给数据存多个历史版本，读的时候读快照，这样读不加锁、读写不阻塞。
三个零件：
1. **隐藏字段**：每行有 `trx_id`（哪个事务改的）、`roll_pointer`（指向上一版本）。
2. **undo log 版本链**：一行数据的历史版本用指针串成链表。
3. **ReadView**：事务读的时候生成一个"当前有哪些事务还没提交"的快照，顺着版本链往下找，找到第一个对自己可见的版本。
**RC 和 RR 的区别就一句话**：
> RC 是**每次查询**都生成新 ReadView，所以能看到别人新提交的 → 不可重复读；
RR 是**第一次查询**生成后一直用，所以整个事务看到的是同一份快照。
---
### 5. 锁
- **按粒度**：表锁（快、冲突多）、行锁（InnoDB，基于索引实现 —— **没走索引会退化成表锁**，这是重点）。
- **按模式**：共享锁 S（读锁）、排他锁 X（写锁）。
- **行锁三种形态**：
	- Record Lock：锁某一行
	- Gap Lock：锁间隙，防止插入（解决幻读）
	- Next-Key Lock：Record + Gap，RR 下默认用这个
- **意向锁**：表级标记，让"要加表锁时"不用逐行检查，直接看标记。
- **死锁**：两个事务互相持有对方要的锁。解决：固定加锁顺序、减小事务粒度、设置超时。
---
### 6. 三大日志（面试爱问区别）
**口述版**：redo 保证不丢（物理日志，InnoDB 的），undo 保证能回滚和 MVCC，binlog 用来主从同步和备份恢复（Server 层的）。
| 日志 | 层级 | 作用 | 内容 |
| --- | --- | --- | --- |
| redo log | InnoDB | 崩溃恢复，保证持久性 | 物理：某页做了什么修改，循环写 |
| undo log | InnoDB | 回滚 + MVCC 版本链 | 逻辑：反向操作 |
| binlog | Server | 主从复制、数据恢复 | 逻辑：SQL 或行变更，追加写 |
**两阶段提交**：
> 为了让 redo log 和 binlog 保持一致。先写 redo（prepare）→ 写 binlog → 再把 redo 置为 commit。中间崩了可以靠 binlog 是否完整来决定提交还是回滚。
---
### 7. SQL 优化思路（能说出流程就赢了）
**口述版**：先用慢查询日志定位，再用 EXPLAIN 看执行计划，重点看 type 和 Extra。
- `type`：从好到坏 `const > eq_ref > ref > range > index > ALL`，看到 **ALL 就是全表扫描**要优化。
- `Extra`：看到 `Using filesort`（额外排序）、`Using temporary`（临时表）要优化；看到 `Using index` 是好事（覆盖索引）。
- 常见手段：加合适的联合索引、覆盖索引避免回表、`limit` 深分页改成 `where id > xxx limit n`、大事务拆小、避免 `select *`。
---
### 8. 分库分表
- **垂直拆分**：按字段/业务拆（用户库、订单库）。
- **水平拆分**：按行拆（用户 ID 取模分到 16 张表）。
- **带来的问题**：跨库 join、分布式事务、全局唯一 ID（雪花算法）、跨库分页。
- **什么时候拆**：单表超过 2000 万行或单表数据量过大，先考虑归档/读写分离，拆分是最后手段。

## 二、Redis 核心
### 1. 为什么快
**口述版**：纯内存操作、单线程避免上下文切换和锁竞争、IO 多路复用、数据结构设计得好。
> 注意说清：Redis 6.0 后**网络 IO 是多线程**的，但**命令执行仍然是单线程**。
---
### 2. 数据结构与使用场景（一定要带场景讲）
| 类型 | 场景 | 底层 |
| --- | --- | --- |
| String | 缓存对象、计数器、分布式锁 | SDS / int |
| Hash | 存对象（可改单个字段） | ziplist / hashtable |
| List | 消息队列、最新列表 | quicklist |
| Set | 去重、共同好友（交集）、抽奖 | intset / hashtable |
| ZSet | 排行榜、延迟队列 | ziplist / **跳表** |
**跳表为什么不用红黑树**：
> 跳表实现简单、支持范围查询天然高效（底层是有序链表），而且并发友好。
**其他**：Bitmap（签到、布隆过滤器）、HyperLogLog（UV 去重统计，有误差但省内存）、GEO（附近的人）、Stream（消息队列）。
---
### 3. 持久化 RDB vs AOF
**口述版**：RDB 是快照，恢复快但可能丢数据；AOF 是记命令，更安全但文件大恢复慢。生产一般混合使用。
|  | RDB | AOF |
| --- | --- | --- |
| 内容 | 某时刻全量快照（二进制） | 每条写命令（文本） |
| 优点 | 文件小、恢复快 | 丢数据少 |
| 缺点 | 可能丢几分钟数据 | 文件大、恢复慢 |
| 刷盘 | fork 子进程，COW 写时复制 | always / **everysec（默认）** / no |
- **AOF 重写**：文件太大时，根据当前内存数据重新生成一份最小命令集。
- **混合持久化（4.0+）**：重写时前半段 RDB 格式 + 后半段增量 AOF —— 兼顾两者，推荐。
---
### 4. 过期删除 + 内存淘汰（容易混，分清）
**过期删除**（key 到期了怎么删）：
- **惰性删除**：访问时才检查删除 —— 省 CPU，费内存。
- **定期删除**：每隔一段时间随机抽查一批 —— 折中。
- Redis 两个**一起用**。
**内存淘汰**（内存满了删谁）—— 8 种策略，记住主线：
- `noeviction`：不删，直接报错（默认）
- `allkeys-lru` / `volatile-lru`：淘汰最久未使用 —— **最常用**
- `allkeys-lfu` / `volatile-lfu`：淘汰使用频率最低
- `allkeys-random` / `volatile-random`：随机
- `volatile-ttl`：淘汰剩余存活时间最短的
> `allkeys-*` 是所有 key，`volatile-*` 是只在设了过期时间的 key 里挑。
---
### 5. 缓存三大问题（必考，记住"穿透/击穿/雪崩"的区别）
| 问题 | 一句话 | 解决 |
| --- | --- | --- |
| **穿透** | 查**根本不存在**的数据，每次都打到 DB | 缓存空值 + 布隆过滤器 + 参数校验 |
| **击穿** | 某个**热点 key** 突然过期，大量请求同时打到 DB | 互斥锁重建 + 热点 key 永不过期（逻辑过期） |
| **雪崩** | **大量 key 同时过期** 或 Redis 挂了 | 过期时间加随机值 + 集群高可用 + 限流降级 |
> 记忆：穿透=没有这个数据；击穿=**一个**点被打穿；雪崩=**一片**全崩。
---
### 6. 缓存与数据库一致性（高频追问）
**口述版**：推荐用 Cache Aside + **先更新数据库，再删除缓存**，这是不一致概率最低的方案。
- **为什么是删除不是更新**：更新缓存可能写入旧值（并发乱序），而且可能写了没人读，浪费。
- **为什么是先 DB 后删缓存**：如果先删缓存，删完还没更新 DB 时有请求进来，会把旧值重新加载进缓存。
- **还是可能不一致怎么办**：
	1. **延迟双删**：更新 DB → 删缓存 → 睡一小会 → 再删一次。
	2. **消息队列/Canal 订阅 binlog** 异步重试删除 —— 生产常用。
	3. 给缓存设**较短过期时间**兜底。
- 结论：**强一致做不到，追求最终一致**。真要强一致就别用缓存，或者加分布式锁（代价很大）。
---
### 7. 分布式锁（能完整讲出演进就很加分）
**口述版**：用 `SET key value NX EX` 一条命令原子加锁，value 放唯一标识，解锁用 Lua 脚本保证"判断+删除"的原子性。
演进过程：
1. `setnx` + `expire` → ❌ 两条命令非原子，中间崩了锁永不释放
2. `SET key val NX EX 30` → ✅ 原子加锁
3. 解锁要先判断 value 是不是自己的 → ❌ 判断和删除非原子 → **用 Lua 脚本**
4. 业务没执行完锁过期了 → **看门狗自动续期**（Redisson 实现）
5. 主从切换锁丢失 → RedLock（争议大，可答"了解但生产谨慎用，强一致场景用 etcd/ZooKeeper"）
**直接说 Redisson 就行**，它把上面全封装了。
---
### 8. 高可用三级演进
**口述版**：主从解决读压力，哨兵解决自动故障转移，集群解决数据量和写压力。
1. **主从复制**：读写分离，主写从读。全量同步（RDB）+ 增量同步（repl_backlog 缓冲区）。**异步复制，所以主挂了可能丢数据**。
2. **哨兵 Sentinel**：监控主节点，主观下线 → 客观下线（多数哨兵同意）→ 选举 leader → 故障转移，通知客户端。解决了**自动切换**，但没解决**容量**。
3. **Cluster 集群**：数据分片，**16384 个哈希槽**，`CRC16(key) % 16384` 决定落在哪个节点。每个分片自己有主从。
	- 为什么是 16384：心跳包里要传槽位图，16384 bit = 2KB，刚好；而且集群节点一般不超过 1000 个，够用。
	- 多 key 操作要用 **hash tag**：`{user1}:name` 和 `{user1}:age` 会落到同一个槽。
---
### 9. 其他高频小点
- **big key 危害**：阻塞单线程、网络打满、删除时卡顿 → 用 `UNLINK` 异步删、拆分 key。
- **热 key 解决**：本地缓存 + key 加随机后缀打散到多个节点。
- **Pipeline**：一次发多条命令，减少 RTT，**不是原子的**。
- **Redis 事务**：`MULTI/EXEC`，**不支持回滚**，只是批量执行 —— 所以通常用 **Lua 脚本**代替。
- **Redis 能做消息队列吗**：List（简单但没 ACK）、Pub/Sub（不持久化，掉线丢消息）、Stream（支持消费组和 ACK，但还是不如 Kafka/RocketMQ 可靠）。

## 三、临场开口的万能模板
被问到任何一个点，按这个结构讲，三十秒就显得很专业：
> **是什么** → **为什么这么设计 / 解决了什么问题** → **怎么用 / 有什么坑** → **（加分）我在项目里怎么用的**
比如问 MVCC：
> "MVCC 是多版本并发控制，核心解决的是读写冲突 —— 传统加锁的话读写互斥，性能很差。它靠三个东西实现：行里的隐藏事务 ID、undo log 组成的版本链、还有 ReadView 快照。读的时候顺着版本链找到对自己可见的版本，所以快照读不加锁。RC 和 RR 的区别就是 ReadView 的生成时机，RC 每次查询都生成，RR 只在第一次生成。不过要注意 MVCC 只对快照读有效，`select for update` 这种当前读还是要加锁的。"
