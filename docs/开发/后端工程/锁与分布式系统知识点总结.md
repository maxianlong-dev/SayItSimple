# 锁与分布式系统知识点总结
---
## 零、为什么需要锁？
### 1. 根本原因：并发下的共享资源竞争
当多个执行单元（线程/进程/服务实例）同时读写同一份共享数据时，如果不加控制，会导致**数据不一致**。
```python
import threading

counter = 0

def increment():
    global counter
    for _ in range(100000):
        counter += 1  # 不是原子操作！

t1 = threading.Thread(target=increment)
t2 = threading.Thread(target=increment)
t1.start(); t2.start()
t1.join(); t2.join()

print(counter)  # 期望 200000，实际可能是 153782、167291 等随机值
```
**为什么结果不对？** `counter += 1` 在 CPU 层面是三步操作：
```plain text
1. 读取 counter 的值到寄存器    (READ)
2. 寄存器值 +1                  (ADD)
3. 写回 counter                 (WRITE)
```
两个线程交错执行时：
```plain text
线程A: READ counter=0
线程B: READ counter=0     ← 读到了同样的旧值
线程A: ADD → 1, WRITE counter=1
线程B: ADD → 1, WRITE counter=1   ← 覆盖了 A 的结果！
                                     两次 +1 只生效了一次
```
这就是**竞态条件（Race Condition）**。
### 2. 加锁后：问题解决
```python
import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    for _ in range(100000):
        with lock:          # 同一时刻只有一个线程能进入
            counter += 1

t1 = threading.Thread(target=increment)
t2 = threading.Thread(target=increment)
t1.start(); t2.start()
t1.join(); t2.join()

print(counter)  # 永远是 200000
```
锁保证了 READ → ADD → WRITE 三步作为一个整体（**临界区**）执行，不会被打断。
### 3. 不只是计数器——锁要保护的典型场景
| 场景 | 不加锁的后果 | 示例 |
| --- | --- | --- |
| 余额扣减 | 超卖/余额为负 | 两人同时买最后一件商品 |
| 链表/队列操作 | 数据结构损坏 | 两线程同时 append 导致节点丢失 |
| 配置热更新 | 读到写了一半的状态 | 读到 host 更新了但 port 还是旧的 |
| 文件写入 | 内容交错/损坏 | 两个进程同时写同一个日志文件 |
| 数据库行更新 | 丢失更新（Lost Update） | 两个事务同时读-改-写同一行 |
### 4. 单机锁 vs 分布式锁——为什么还需要分布式锁？
```plain text
单机环境：
  线程A ─┐
  线程B ─┼─ 同一个进程 → threading.Lock 就够了
  线程C ─┘

分布式环境：
  服务实例1 (机器A) ─┐
  服务实例2 (机器B) ─┼─ 不同进程、不同机器 → 内存中的锁彼此不可见！
  服务实例3 (机器C) ─┘
```
**单机锁只在同一进程内存中有效。** 当系统部署多个实例时，需要一个所有实例都能看到的"外部锁"——这就是分布式锁（基于 Redis / ZooKeeper / MySQL 等外部存储）。
```python
# 单机锁：只能保护本进程内的线程
lock = threading.Lock()  # 其他机器上的进程感知不到这个锁

# 分布式锁：所有实例通过同一个 Redis 协调
# 机器 A 加锁成功 → 机器 B/C 尝试加锁会失败（等待）
token = redis_client.set("lock:order:123", "machine_a", nx=True, ex=30)
```
### 5. 锁的本质与代价
**锁的本质：** 把并行变成串行，用"等待"换"正确性"。
**代价：**
| 代价 | 说明 |
| --- | --- |
| 性能下降 | 并发度降低，线程排队等待 |
| 死锁风险 | 多个锁交叉获取可能永久阻塞 |
| 复杂度 | 锁的粒度、顺序、超时都需要仔细设计 |
**设计原则：**
- 锁的粒度尽量小（只锁必须锁的部分）
- 持有锁的时间尽量短（不要在锁内做 I/O）
- 能用无锁方案（CAS、队列、Actor）就不用锁
- 分布式场景优先考虑"最终一致性"而非"强一致锁"

## 一、本地锁（单机锁）
> 以下用 Python 的 `threading` 和 `multiprocessing` 模块讲解锁的概念。
### 1. threading.Lock（互斥锁）
最基本的锁，同一时刻只有一个线程可以持有。
```python
import threading

lock = threading.Lock()

# 方式一：手动 acquire / release
lock.acquire()
try:
    # 临界区
    shared_counter += 1
finally:
    lock.release()

# 方式二：上下文管理器（推荐，自动释放）
with lock:
    shared_counter += 1
```
**注意：** Lock 不可重入，同一线程重复 acquire 会死锁。
### 2. threading.RLock（可重入锁）
同一线程可以多次 acquire，不会死锁，需对应次数 release。
```python
import threading

rlock = threading.RLock()

def recursive_func(n):
    with rlock:
        if n > 0:
            recursive_func(n - 1)  # 同一线程可重复获取锁

# 可重入：内部计数器记录 acquire 次数
rlock.acquire()
rlock.acquire()   # 不会死锁（Lock 会死锁）
rlock.release()
rlock.release()   # 必须 release 相同次数
```
**Lock vs RLock 对比：**
| 特性 | Lock | RLock |
| --- | --- | --- |
| 可重入 | 否（死锁） | 是 |
| 性能 | 略高 | 略低（维护计数器） |
| 适用场景 | 简单互斥 | 递归、嵌套调用 |
### 3. threading.Condition（条件变量）
在锁的基础上实现线程间通信（等待/通知模式）。
```python
import threading
import queue

cond = threading.Condition()
items = []

# 生产者
def producer():
    with cond:
        items.append("data")
        cond.notify()      # 通知一个等待线程
        # cond.notify_all()  # 通知所有等待线程

# 消费者
def consumer():
    with cond:
        while not items:        # 必须用 while（防止虚假唤醒）
            cond.wait()         # 释放锁并等待通知
        item = items.pop(0)     # 被唤醒后重新获取锁
```
**wait_for 简化写法（Python 3.2+）：**
```python
with cond:
    cond.wait_for(lambda: len(items) > 0)  # 等待条件为真
    item = items.pop(0)
```
### 4. threading.Semaphore（信号量）
控制同时访问资源的线程数量。
```python
import threading

# 最多允许 5 个线程同时访问
sem = threading.Semaphore(5)

def access_resource():
    with sem:  # acquire() 计数器 -1，release() 计数器 +1
        # 访问受限资源（如数据库连接池）
        do_work()

# BoundedSemaphore：release 次数不能超过 acquire 次数（更安全）
bounded_sem = threading.BoundedSemaphore(5)
```
### 5. threading.Event（事件）
线程间简单信号通知，无需配合锁。
```python
import threading

event = threading.Event()

# 等待方
def worker():
    event.wait()         # 阻塞直到 event 被 set
    # event.wait(timeout=5)  # 超时等待
    do_work()

# 通知方
def controller():
    event.set()          # 唤醒所有等待线程
    # event.clear()      # 重置为未触发状态
    # event.is_set()     # 检查状态
```
### 6. threading.Barrier（屏障）
N 个线程互相等待，全部到齐后一起执行。
```python
import threading

barrier = threading.Barrier(3)  # 需要 3 个线程到齐

def worker(name):
    print(f"{name} 准备就绪")
    barrier.wait()              # 阻塞直到 3 个线程都调用了 wait
    print(f"{name} 开始执行")   # 3 个线程同时继续
```
### 7. 读写锁（自行实现 / 第三方库）
Python 标准库没有 ReadWriteLock，可以用 Condition 实现：
```python
import threading

class ReadWriteLock:
    def __init__(self):
        self._lock = threading.Condition(threading.Lock())
        self._readers = 0
        self._writers = 0
        self._write_waiters = 0

    def acquire_read(self):
        with self._lock:
            while self._writers > 0 or self._write_waiters > 0:
                self._lock.wait()
            self._readers += 1

    def release_read(self):
        with self._lock:
            self._readers -= 1
            if self._readers == 0:
                self._lock.notify_all()

    def acquire_write(self):
        with self._lock:
            self._write_waiters += 1
            while self._readers > 0 or self._writers > 0:
                self._lock.wait()
            self._write_waiters -= 1
            self._writers += 1

    def release_write(self):
        with self._lock:
            self._writers -= 1
            self._lock.notify_all()
```
### 8. GIL（全局解释器锁）
CPython 的特殊机制，理解 Python 锁必须了解 GIL。
```plain text
GIL：同一时刻只有一个线程执行 Python 字节码
         ↓
CPU 密集型 → 多线程无法并行 → 应使用 multiprocessing
I/O 密集型 → 线程在等待 I/O 时释放 GIL → 多线程仍有效
```
| 场景 | 推荐方案 |
| --- | --- |
| I/O 密集（网络、文件） | threading / asyncio |
| CPU 密集（计算） | multiprocessing / C 扩展 |
| 混合场景 | concurrent.futures（线程池 + 进程池） |
### 9. multiprocessing 中的锁
多进程场景下需要进程级别的锁：
```python
from multiprocessing import Process, Lock, Value

def worker(lock, counter):
    for _ in range(10000):
        with lock:
            counter.value += 1

if __name__ == "__main__":
    lock = Lock()
    counter = Value('i', 0)     # 共享内存
    processes = [Process(target=worker, args=(lock, counter)) for _ in range(4)]
    for p in processes:
        p.start()
    for p in processes:
        p.join()
    print(counter.value)        # 40000
```
### 10. concurrent.futures（高级并发接口）
线程池 / 进程池统一接口，简化并发编程：
```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def fetch_url(url):
    # I/O 操作
    return requests.get(url).text

with ThreadPoolExecutor(max_workers=10) as executor:
    futures = {executor.submit(fetch_url, url): url for url in urls}
    for future in as_completed(futures):
        url = futures[future]
        result = future.result()  # 获取结果（会抛异常）
```
### 11. asyncio 中的锁（协程锁）
异步编程中保护共享状态：
```python
import asyncio

lock = asyncio.Lock()

async def safe_update(shared_data):
    async with lock:
        # 协程安全的临界区
        value = shared_data["count"]
        await asyncio.sleep(0.1)  # 模拟异步操作
        shared_data["count"] = value + 1

# asyncio 也提供 Semaphore、Event、Condition
sem = asyncio.Semaphore(10)
async def limited_request():
    async with sem:
        await do_request()
```
### 12. 各同步原语总结
| 原语 | 模块 | 用途 | 关键特性 |
| --- | --- | --- | --- |
| Lock | threading | 基本互斥 | 不可重入 |
| RLock | threading | 可重入互斥 | 同线程可重复获取 |
| Condition | threading | 等待/通知 | 配合 while 循环使用 |
| Semaphore | threading | 限制并发数 | 计数器 |
| Event | threading | 简单信号 | set/wait/clear |
| Barrier | threading | 集合点同步 | N 个线程到齐才继续 |
| Lock | multiprocessing | 进程间互斥 | 跨进程 |
| Lock | asyncio | 协程互斥 | async with |
### 13. 死锁与避免
```python
# 死锁示例：两个锁交叉获取
lock_a = threading.Lock()
lock_b = threading.Lock()

def thread_1():
    with lock_a:
        with lock_b:     # 等待 lock_b
            pass

def thread_2():
    with lock_b:
        with lock_a:     # 等待 lock_a → 死锁！
            pass

# 解决方案 1：统一加锁顺序
def thread_1_fixed():
    with lock_a:         # 所有线程都先获取 lock_a
        with lock_b:
            pass

# 解决方案 2：超时获取
acquired = lock_a.acquire(timeout=5)
if not acquired:
    # 获取失败，避免死锁
    handle_timeout()

# 解决方案 3：使用 contextlib 统一管理
import contextlib

@contextlib.contextmanager
def acquire_locks(*locks):
    sorted_locks = sorted(locks, key=id)  # 按 id 排序，保证顺序一致
    try:
        for lock in sorted_locks:
            lock.acquire()
        yield
    finally:
        for lock in reversed(sorted_locks):
            lock.release()

with acquire_locks(lock_a, lock_b):
    pass
```
**死锁四个必要条件：**
1. 互斥：资源同一时刻只能一个线程持有
2. 持有并等待：持有一个锁的同时等待另一个
3. 不可抢占：锁不能被强制释放
4. 循环等待：线程间形成环形等待链
**避免策略：** 打破任一条件即可（通常打破"循环等待"——统一加锁顺序）

## 二、分布式锁
### 1. 分布式锁核心要求
| 要求 | 说明 |
| --- | --- |
| 互斥性 | 同一时刻只有一个客户端持有锁 |
| 防死锁 | 持有者崩溃后锁能自动释放（超时机制） |
| 可重入 | 同一客户端可多次加锁 |
| 高可用 | 锁服务本身要高可用 |
| 安全释放 | 只能由加锁者释放（唯一标识） |
### 2. 基于 Redis 的分布式锁
#### 基本实现
```bash
# 加锁（原子操作：设值 + 过期时间）
SET lock_key <unique_id> NX EX 30

# 解锁（Lua 脚本保证原子性）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```
#### 存在的问题
| 问题 | 描述 | 解决方案 |
| --- | --- | --- |
| 锁过期但业务未完成 | 业务执行时间 \> 锁过期时间 | 看门狗续期（Redisson） |
| 主从切换丢锁 | Master 宕机，Slave 未同步到锁 | RedLock 算法 |
| 不可重入 | 同一线程再次加锁失败 | Hash 结构 + 计数器 |
#### Python redis-py 实现
```python
import redis
import uuid
import time

r = redis.Redis()

def acquire_lock(lock_name, expire=30):
    """加锁：SET NX EX 原子操作"""
    token = str(uuid.uuid4())
    acquired = r.set(lock_name, token, nx=True, ex=expire)
    return token if acquired else None

def release_lock(lock_name, token):
    """解锁：Lua 脚本保证原子性"""
    lua_script = """
    if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
    else
        return 0
    end
    """
    return r.eval(lua_script, 1, lock_name, token)

# 使用方式
token = acquire_lock("order:123")
if token:
    try:
        # 业务逻辑
        process_order()
    finally:
        release_lock("order:123", token)
```
#### 带看门狗续期的实现
```python
import threading

class RedisLock:
    def __init__(self, redis_client, name, expire=30):
        self._redis = redis_client
        self._name = name
        self._expire = expire
        self._token = None
        self._watchdog = None
        self._released = threading.Event()

    def acquire(self):
        self._token = str(uuid.uuid4())
        acquired = self._redis.set(self._name, self._token, nx=True, ex=self._expire)
        if acquired:
            self._start_watchdog()
        return bool(acquired)

    def release(self):
        self._released.set()
        if self._watchdog:
            self._watchdog.join()
        release_lock(self._name, self._token)

    def _start_watchdog(self):
        """看门狗：每 expire/3 秒续期一次"""
        def renew():
            interval = self._expire // 3
            while not self._released.wait(timeout=interval):
                self._redis.expire(self._name, self._expire)
        self._watchdog = threading.Thread(target=renew, daemon=True)
        self._watchdog.start()

    def __enter__(self):
        self.acquire()
        return self

    def __exit__(self, *args):
        self.release()

# 使用方式
with RedisLock(r, "order:123"):
    process_order()
```
#### python-redis-lock 第三方库（推荐生产使用）
```python
import redis_lock

# 自动续期、可重入、上下文管理器
conn = redis.Redis()
lock = redis_lock.Lock(conn, "my-lock", expire=30, auto_renewal=True)

with lock:
    # 自动续期，业务执行完自动释放
    process()
```
**看门狗机制原理：**
```plain text
加锁成功 → 启动后台线程 → 每 expire/3 续期一次
                         → 客户端宕机则停止续期 → 锁自动过期释放
```
**可重入原理（Hash 结构）：**
```bash
HSET lock_key client_id:thread_id 1   # 第一次加锁
HINCRBY lock_key client_id:thread_id 1 # 重入，计数+1
HINCRBY lock_key client_id:thread_id -1 # 解锁，计数-1
# 计数为 0 时删除 key
```
#### RedLock 算法
针对 Redis 主从切换丢锁问题，向 N 个独立 Redis 实例加锁：
```plain text
1. 获取当前时间 T1
2. 依次向 N 个实例发送 SET NX EX
3. 当 >= N/2+1 个实例加锁成功，且总耗时 < 锁超时时间 → 加锁成功
4. 锁的实际有效时间 = 超时时间 - 加锁耗时
5. 加锁失败则向所有实例发送解锁
```
**Python pottery 库实现 RedLock：**
```python
from pottery import Redlock
from redis import Redis

redis_masters = [
    Redis(host="redis1", port=6379),
    Redis(host="redis2", port=6379),
    Redis(host="redis3", port=6379),
]

lock = Redlock(key="my-resource", masters=redis_masters, auto_release_time=30)
with lock:
    process()
```
**争议：** Martin Kleppmann 指出 RedLock 在网络分区和 GC 停顿下仍不安全，建议搭配 fencing token 使用。
### 3. 基于 ZooKeeper 的分布式锁
利用 ZK 的临时顺序节点 + Watch 机制。
```plain text
/locks/resource_name
    ├── _c_0000000001  (客户端 A)
    ├── _c_0000000002  (客户端 B)
    └── _c_0000000003  (客户端 C)
```
**加锁流程：**
1. 在 `/locks/resource` 下创建临时顺序节点
2. 获取所有子节点，判断自己是否是最小序号
3. 是 → 加锁成功
4. 否 → Watch 前一个节点的删除事件，阻塞等待
**Python kazoo 库实现：**
```python
from kazoo.client import KazooClient
from kazoo.recipe.lock import Lock as ZkLock

zk = KazooClient(hosts="127.0.0.1:2181")
zk.start()

# 方式一：使用内置 recipe
lock = ZkLock(zk, "/locks/my-resource")
with lock:
    # 持有锁期间执行业务
    process()

# 方式二：带超时
acquired = lock.acquire(timeout=10)  # 最多等 10 秒
if acquired:
    try:
        process()
    finally:
        lock.release()

zk.stop()
```
**优点：**
- 天然防死锁（临时节点，会话断开自动删除）
- 顺序公平
- Watch 机制避免惊群效应
**缺点：** 性能低于 Redis（ZK 写入需要多数派同步）
### 4. 基于 MySQL 的分布式锁
#### 方式一：唯一索引
```python
import pymysql
import time

def acquire_db_lock(conn, lock_name, owner, expire_seconds=30):
    """基于唯一索引加锁"""
    try:
        with conn.cursor() as cursor:
            cursor.execute(
                "INSERT INTO distributed_lock (lock_name, owner, expire_time) "
                "VALUES (%s, %s, NOW() + INTERVAL %s SECOND)",
                (lock_name, owner, expire_seconds)
            )
        conn.commit()
        return True
    except pymysql.IntegrityError:
        return False  # 唯一索引冲突，加锁失败

def release_db_lock(conn, lock_name, owner):
    """只能由加锁者释放"""
    with conn.cursor() as cursor:
        cursor.execute(
            "DELETE FROM distributed_lock WHERE lock_name=%s AND owner=%s",
            (lock_name, owner)
        )
    conn.commit()
```
#### 方式二：悲观锁（FOR UPDATE）
```python
def pessimistic_lock_example(conn, resource_id):
    """SELECT FOR UPDATE 行级锁"""
    try:
        conn.begin()
        with conn.cursor() as cursor:
            cursor.execute(
                "SELECT * FROM resource WHERE id=%s FOR UPDATE", (resource_id,)
            )
            row = cursor.fetchone()
            # 业务操作
            cursor.execute(
                "UPDATE resource SET data='new_value' WHERE id=%s", (resource_id,)
            )
        conn.commit()
    except Exception:
        conn.rollback()
```
#### 方式三：乐观锁（版本号）
```python
def optimistic_lock_update(conn, resource_id, new_data):
    """CAS 风格的乐观锁"""
    with conn.cursor() as cursor:
        cursor.execute("SELECT version FROM resource WHERE id=%s", (resource_id,))
        old_version = cursor.fetchone()["version"]

        affected = cursor.execute(
            "UPDATE resource SET data=%s, version=version+1 "
            "WHERE id=%s AND version=%s",
            (new_data, resource_id, old_version)
        )
        conn.commit()
        if affected == 0:
            raise Exception("乐观锁冲突，需要重试")
```
### 5. 三种方案对比
| 维度 | Redis | ZooKeeper | MySQL |
| --- | --- | --- | --- |
| 性能 | 高（内存） | 中 | 低（磁盘 I/O） |
| 可靠性 | 中（主从可能丢锁） | 高（ZAB 协议） | 高（事务） |
| 实现复杂度 | 中 | 高 | 低 |
| 公平性 | 非公平 | 公平（顺序节点） | 取决于实现 |
| 适用场景 | 高并发，允许极端情况不一致 | 强一致要求 | 并发量低 |

## 三、分布式系统理论
### 1. CAP 定理
分布式系统不可能同时满足以下三者，最多只能满足两个：
| 属性 | 含义 |
| --- | --- |
| C（Consistency） | 所有节点看到相同数据（线性一致性） |
| A（Availability） | 每个请求都能得到非错误响应 |
| P（Partition Tolerance） | 网络分区时系统仍能运行 |
**实际选择（P 必须保证）：**
- **CP：** ZooKeeper、Etcd、HBase — 分区时拒绝不一致的读写
- **AP：** Eureka、Cassandra、DynamoDB — 分区时允许返回旧数据
### 2. BASE 理论
对 CAP 中 AP 的扩展，核心思想是最终一致性。
| 概念 | 含义 |
| --- | --- |
| BA（Basically Available） | 基本可用，允许降级响应 |
| S（Soft State） | 软状态，允许中间状态存在 |
| E（Eventually Consistent） | 最终一致，经过一段时间后数据一致 |
### 3. 一致性模型
```plain text
强一致性 > 线性一致性 > 顺序一致性 > 因果一致性 > 最终一致性
```
| 模型 | 说明 | 代表 |
| --- | --- | --- |
| 强一致性 | 写后立即可读到最新值 | 单机数据库 |
| 线性一致性 | 操作按全局时间线有序 | Raft/ZAB |
| 最终一致性 | 经过不确定时间后一致 | DNS、Redis 主从 |
| 因果一致性 | 有因果关系的操作有序 | CRDT |
### 4. 共识算法
#### Paxos
- 理论基础，难以工程实现
- 角色：Proposer、Acceptor、Learner
- 两阶段：Prepare → Accept
#### Raft（易理解的 Paxos）
```plain text
Leader 选举 → 日志复制 → 安全性保证
```
**核心机制：**
- **Leader 选举：** Term（任期）+ 随机超时 + 多数派投票
- **日志复制：** Leader 接收写请求，复制到多数 Follower 后提交
- **安全性：** 只有包含最新已提交日志的节点才能当选 Leader
**应用：** Etcd、Consul、TiKV、CockroachDB
#### ZAB（ZooKeeper Atomic Broadcast）
类似 Raft，但专为 ZooKeeper 设计：
- 崩溃恢复模式（选主）
- 消息广播模式（同步数据）
- 事务 ID（ZXID）全局有序
### 5. Gossip 协议
去中心化的信息传播协议，节点间随机交换信息。
**特点：** 最终一致、容错性强、扩展性好
**应用：** Redis Cluster 节点通信、Consul 成员管理

## 四、分布式事务
### 1. 2PC（两阶段提交）
```plain text
协调者                   参与者
  |--- Prepare(准备) --->|
  |<-- Yes/No -----------|
  |                      |
  |--- Commit/Rollback ->|
  |<-- ACK --------------|
```
**问题：** 同步阻塞、单点故障（协调者）、数据不一致（网络异常）
### 2. 3PC（三阶段提交）
在 2PC 基础上增加 CanCommit 阶段，引入超时机制减少阻塞。
```plain text
CanCommit → PreCommit → DoCommit
```
### 3. TCC（Try-Confirm-Cancel）
业务层面的分布式事务，每个参与者实现三个接口。
```plain text
Try：      资源预留（冻结库存、冻结金额）
Confirm：  确认提交（扣减库存、扣减金额）
Cancel：   取消回滚（释放库存、释放金额）
```
**适用：** 对一致性要求高、需要灵活控制的场景（转账、下单）
**难点：**
- 空回滚：Try 未执行，Cancel 被调用 → Cancel 需判断 Try 是否执行过
- 悬挂：Cancel 先于 Try 到达 → Try 需检查是否已 Cancel
- 幂等：Confirm/Cancel 可能重试 → 需保证幂等
### 4. Saga 模式
长事务拆分为多个本地事务，每个事务有对应的补偿操作。
```plain text
T1 → T2 → T3 → ... → Tn
         ↓（T3 失败）
C2 ← C1  （逆序补偿）
```
**两种实现：**
- **编排（Choreography）：** 事件驱动，各服务监听事件
- **协调（Orchestration）：** 中心协调器控制流程
**适用：** 跨服务长流程（订单、物流、支付）
### 5. 本地消息表
```plain text
1. 业务操作 + 写消息表（同一本地事务）
2. 后台轮询消息表，发送到 MQ
3. 消费方消费消息，处理业务
4. 处理成功后回调确认
```
### 6. 可靠消息最终一致性（RocketMQ 事务消息）
```plain text
1. 发送半消息（Half Message）→ MQ（不可消费）
2. 执行本地事务
3. 根据本地事务结果：
   - 成功 → Commit（消息可消费）
   - 失败 → Rollback（删除消息）
4. MQ 回查机制处理未确认的半消息
```
### 7. 最大努力通知
适用于对一致性要求不高的场景（如支付结果通知）：
- 发送方尽最大努力通知接收方
- 接收方提供查询接口供对账
### 8. 各方案对比
| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
| --- | --- | --- | --- | --- |
| 2PC/XA | 强一致 | 低 | 低 | 数据库层面、短事务 |
| TCC | 强一致 | 中 | 高 | 资金、库存等核心业务 |
| Saga | 最终一致 | 高 | 中 | 长流程、跨服务编排 |
| 本地消息表 | 最终一致 | 高 | 中 | 异步解耦场景 |
| 事务消息 | 最终一致 | 高 | 低 | 依赖 MQ 的场景 |

## 五、分布式 ID 生成
### 1. UUID
```python
import uuid

uid = uuid.uuid4()          # 128 位，全球唯一
str(uid)                    # 'a8098c1a-f86e-11da-bd1a-00112444be1e'
uid.hex                     # 去掉横线的 32 字符
```
**优点：** 本地生成、无依赖
**缺点：** 无序（B+ 树页分裂）、太长（32 字符）、无业务含义
### 2. 数据库自增
```sql
-- 单机
AUTO_INCREMENT

-- 多机（步长分配）
-- 机器 1：1, 3, 5, 7...（step=2, offset=1）
-- 机器 2：2, 4, 6, 8...（step=2, offset=2）
```
### 3. 号段模式（Leaf-Segment）
每次从 DB 批量获取一段 ID，本地分配：
```plain text
DB: max_id=1000, step=1000
应用获取 [1001, 2000] 这一段，内存中自增分配
快用完时异步加载下一段 → 双 Buffer 无阻塞
```
### 4. Snowflake（雪花算法）
```plain text
0 | 41 位时间戳 | 10 位机器 ID | 12 位序列号
  |  69年够用   | 1024 台机器  | 每毫秒 4096 个
```
**64 位 Long 型，趋势递增，可反解时间。**
**Python 实现：**
```python
import time
import threading

class Snowflake:
    def __init__(self, worker_id, datacenter_id):
        self.worker_id = worker_id & 0x1F         # 5 位
        self.datacenter_id = datacenter_id & 0x1F  # 5 位
        self.sequence = 0
        self.last_timestamp = -1
        self._lock = threading.Lock()
        self._epoch = 1609459200000  # 2021-01-01 作为起始时间

    def generate(self):
        with self._lock:
            ts = int(time.time() * 1000)
            if ts == self.last_timestamp:
                self.sequence = (self.sequence + 1) & 0xFFF  # 12 位序列号
                if self.sequence == 0:
                    while ts <= self.last_timestamp:
                        ts = int(time.time() * 1000)
            else:
                self.sequence = 0
            self.last_timestamp = ts
            return ((ts - self._epoch) << 22 |
                    self.datacenter_id << 17 |
                    self.worker_id << 12 |
                    self.sequence)

sf = Snowflake(worker_id=1, datacenter_id=1)
uid = sf.generate()
```
**问题与解决：**
- 时钟回拨 → 等待 / 报错 / 扩展位存储
- 机器 ID 分配 → ZooKeeper / 配置中心
### 5. 各方案对比
| 方案 | 有序性 | 性能 | 依赖 | 适用 |
| --- | --- | --- | --- | --- |
| UUID | 无序 | 极高 | 无 | 日志 traceId |
| DB 自增 | 有序 | 低 | DB | 小规模 |
| 号段模式 | 趋势递增 | 高 | DB | 通用 |
| Snowflake | 趋势递增 | 极高 | 时钟 | 高并发 |

## 七、分布式容错
### 1. 超时与重试
```python
import time
import random

def retry_with_backoff(func, max_retries=3, base_delay=1):
    """指数退避重试"""
    for attempt in range(max_retries):
        try:
            return func()
        except Exception as e:
            if attempt == max_retries - 1:
                raise
            delay = base_delay * (2 ** attempt) + random.uniform(0, 1)
            time.sleep(delay)
```
**幂等性保证：**
- 唯一请求 ID + 去重表
- 数据库唯一约束
- Token 机制（先获取 token，请求时携带，一次性消费）
### 2. 熔断器（Circuit Breaker）
```plain text
Closed（正常） → 失败率超阈值 → Open（熔断，快速失败）
                                    ↓ 超时后
                              Half-Open（试探）
                                    ↓ 成功
                              Closed（恢复）
```
**实现：** Hystrix（已停更）、Sentinel、Resilience4j
### 3. 限流
| 算法 | 原理 | 特点 |
| --- | --- | --- |
| 计数器 | 固定窗口内计数 | 简单，有临界突刺 |
| 滑动窗口 | 细分时间片 | 平滑，内存消耗 |
| 漏桶 | 固定速率流出 | 严格匀速 |
| 令牌桶 | 固定速率放令牌 | 允许突发流量 |
**令牌桶（最常用）：**
```plain text
每秒放入 N 个令牌 → 桶满则丢弃
请求到来 → 取到令牌则通过 → 取不到则拒绝/等待
```
### 4. 降级
- **手动降级：** 开关控制，直接返回兜底数据
- **自动降级：** 超时/异常率触发，返回缓存/默认值
- **读降级：** 主库不可用时读从库/缓存
- **写降级：** 同步写改异步写（先写 MQ）
### 5. 故障隔离
- **线程池隔离：** 不同服务调用用不同线程池
- **信号量隔离：** 限制并发调用数
- **进程隔离：** 微服务拆分
- **机房隔离：** 同城双活、异地多活

## 十、经典面试问题
### 1. 如何保证缓存与数据库一致性？
| 方案 | 做法 | 问题 |
| --- | --- | --- |
| Cache Aside | 先更新 DB，再删缓存 | 极端情况短暂不一致 |
| 延迟双删 | 更新 DB → 删缓存 → 延迟再删一次 | 延迟时间难定 |
| 订阅 Binlog | Canal 监听 Binlog → 更新缓存 | 异步，有延迟 |
### 2. 如何设计一个高可用系统？
```plain text
冗余：多副本、多机房
容错：熔断、降级、限流、超时重试
隔离：服务隔离、数据隔离、故障域隔离
监控：指标、日志、链路追踪、告警
演练：混沌工程（Chaos Monkey）、故障注入
```
### 3. 分布式系统如何处理脑裂？
- **Quorum 机制：** 多数派才能提供服务（n/2 + 1）
- **Fencing：** epoch/fencing token，旧 Leader 的请求被拒绝
- **租约（Lease）：** 带有效期的锁，过期自动失效
- **STONITH：** 直接隔离（关机）少数派节点
### 4. 如何实现幂等？
| 场景 | 方案 |
| --- | --- |
| 创建操作 | 唯一业务 ID + 数据库唯一索引 |
| 更新操作 | 乐观锁（版本号）/ 状态机 |
| 消息消费 | 消息 ID 去重表 |
| 接口请求 | Token 令牌（一次性消费） |

## 十一、核心原则总结
| 原则 | 含义 |
| --- | --- |
| 幂等 | 重复执行结果不变 |
| 超时控制 | 任何远程调用必须设超时 |
| 快速失败 | 不等不猜，快速返回错误 |
| 最终一致 | 接受短暂不一致，保证最终正确 |
| 无状态 | 服务无状态，状态外置（DB/缓存） |
| 异步化 | 非核心链路异步处理 |
| 可观测 | 指标 + 日志 + 链路缺一不可 |
