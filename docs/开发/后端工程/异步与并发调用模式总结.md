# 异步与并发调用模式总结
按"调用方对结果的控制程度"从松到紧排列。核心权衡点是：**这个调用的结果，调用方需要负责吗？**
| 模式 | 阻塞调用方 | 关心结果 | 可靠性 | 典型场景 |
| --- | --- | --- | --- | --- |
| 同步阻塞 | 是 | 是 | 取决于下游 | 简单请求、必须等结果 |
| Fire-and-forget | 否 | 否 | 低 | 日志、埋点、非关键通知 |
| 异步带回调 | 否 | 是（回调里） | 低 | 事件触发 |
| Future / Promise | 否（可选） | 可选 | 中 | 可组合的异步步骤 |
| Await / async-await | 否（但等结果） | 是 | 中 | 顺序化异步逻辑 |
| 扇出-聚合 Gather | 短暂 | 全部 | 中 | 并发取 N 个结果 |
| 竞速 First-wins | 短暂 | 第一个 | 中 | 多副本读、超时降级 |
| 流式 Streaming | 否 | 逐项 | 中 | 大数据、实时数据 |
| 可靠投递 MQ/Outbox | 否 | 最终一致 | 高 | 扣款、状态变更、必须执行 |
---
## 1. 同步阻塞（Sync Blocking）
直接调用并死等结果。最简单，但调用方线程被占住，吞吐最差。
```python
import requests

def get_user(uid: int) -> dict:
    # 线程一直阻塞直到响应返回
    resp = requests.get(f"https://api.example.com/users/{uid}")
    return resp.json()

user = get_user(42)  # 调用方在这里干等
print(user)
```
**使用场景：** 必须拿到结果才能继续、调用量小、对延迟不敏感。简单脚本、CLI 工具、内部低频管理接口。
---
## 2. Fire-and-forget（发完就忘）
发起操作后立即返回，不等待结果、不处理响应、不关心是否成功。
```python
import asyncio
import logging

logger = logging.getLogger(__name__)

# 保存任务引用，避免被 GC 回收（asyncio 官方警告）
_background_tasks: set[asyncio.Task] = set()

def fire_and_forget(coro):
    task = asyncio.create_task(coro)
    _background_tasks.add(task)
    task.add_done_callback(_background_tasks.discard)
    return task

async def send_notification(msg: str):
    try:
        await http_client.post("/notify", json={"msg": msg})
    except Exception:
        # 任务内部自己兜底异常，否则会让事件循环报错
        logger.exception("notification failed")

async def handle_request():
    result = do_business_logic()
    fire_and_forget(send_notification("done"))  # 不 await
    return result
```
**使用场景：** 丢了也无所谓的操作——日志上报、埋点打点、非关键通知（邮件/钉钉）、缓存预热、统计计数。
**注意：** 1) 不 await 只是表象；2) 必须保存 Task 引用防止被 GC；3) 任务内部必须自己处理异常。三者缺一不可。
---
## 3. 异步带回调（Callback）
发起时不阻塞，注册回调函数，结果到达时触发。
```python
import asyncio

def on_done(fut: asyncio.Future):
    if fut.exception():
        print("failed:", fut.exception())
    else:
        print("result:", fut.result())

async def fetch_data():
    await asyncio.sleep(1)
    return 42

async def main():
    task = asyncio.create_task(fetch_data())
    task.add_done_callback(on_done)  # 结果就绪时回调
    # 调用方继续干别的
    await asyncio.sleep(2)

asyncio.run(main())
```
**使用场景：** 事件驱动系统、需要"结果到了再触发某段逻辑"但不想阻塞当前流程。GUI、事件总线、底层框架 API。
**缺点：** 回调嵌套容易形成"回调地狱"，可读性差，现代代码多用 async/await 替代。
---
## 4. Future / Promise
返回一个句柄，可选择何时等待、是否等待、如何组合。
```python
import asyncio

async def fetch_user(uid: int) -> dict:
    await asyncio.sleep(0.5)
    return {"id": uid, "name": "alice"}

async def fetch_orders(uid: int) -> list:
    await asyncio.sleep(0.5)
    return [{"oid": 1}, {"oid": 2}]

async def main():
    # 先把两个任务"发出去"，拿到 Task 句柄
    user_task = asyncio.create_task(fetch_user(42))
    order_task = asyncio.create_task(fetch_orders(42))

    # 此处可以做其他事...
    print("doing other work")

    # 想要结果时再 await
    user = await user_task
    orders = await order_task
    print(user, orders)

asyncio.run(main())
```
**使用场景：** 需要灵活控制——可以提前发起、延后等待，或把多个 Future 组合交给上层。构建异步库、需要"提前发起 + 延后消费"的流水线。
---
## 5. Await / async-await（同步式异步）
写起来像顺序代码，但底层非阻塞。等待单个结果时最自然，结果、异常、取消都在当前上下文处理。
```python
import asyncio
import aiohttp

async def fetch_user(session: aiohttp.ClientSession, uid: int) -> dict:
    async with session.get(f"https://api.example.com/users/{uid}") as resp:
        resp.raise_for_status()  # 异常直接抛到当前上下文
        return await resp.json()

async def main():
    async with aiohttp.ClientSession() as session:
        try:
            user = await fetch_user(session, 42)  # 非阻塞等待
            print(user)
        except aiohttp.ClientError as e:
            print("请求失败:", e)

asyncio.run(main())
```
**使用场景：** 业务主流程的异步化——IO 密集型服务、需要顺序处理但不想阻塞线程。现代异步代码的默认写法。
---
## 6. 扇出-聚合（Fan-out / Gather）
并发发出多个调用，等全部完成再继续。
```python
import asyncio
import aiohttp

async def fetch_one(session, url):
    async with session.get(url) as r:
        return await r.json()

async def main():
    urls = ["url1", "url2", "url3"]
    async with aiohttp.ClientSession() as session:
        # 并发发起，gather 等所有完成
        results = await asyncio.gather(
            *(fetch_one(session, u) for u in urls),
            return_exceptions=True,  # 单个失败不抛，返回 Exception 对象
        )
        for url, r in zip(urls, results):
            if isinstance(r, Exception):
                print(f"{url} 失败: {r}")
            else:
                print(f"{url} -> {r}")

asyncio.run(main())
```
**使用场景：** 需要把 N 个独立结果组装起来——聚合多数据源、批量查询、并行抓取。把 N 次串行 IO 压到 1 次 IO 的延迟。
**变体：** `asyncio.gather`（全成功才算成功）、`asyncio.as_completed`（谁先完成先处理谁，不等齐）。
---
## 7. 竞速（First-wins / Race）
并发发出多个调用，只取第一个成功的结果，其余取消。
```python
import asyncio

async def fetch_from_primary():
    await asyncio.sleep(1.0)
    return "primary"

async def fetch_from_secondary():
    await asyncio.sleep(0.3)
    return "secondary"

async def first_wins(*coros):
    tasks = [asyncio.ensure_future(c) for c in coros]
    try:
        # 等第一个完成
        done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
        winner = next(iter(done)).result()
        return winner
    finally:
        # 取消其余任务，避免泄漏
        for t in pending:
            t.cancel()
        # 等待取消真正生效
        await asyncio.gather(*pending, return_exceptions=True)

async def main():
    result = await first_wins(fetch_from_primary(), fetch_from_secondary())
    print("winner:", result)  # secondary

asyncio.run(main())
```
**使用场景：** 多副本读（哪个快用哪个）、超时降级（主 + 备，谁先回用谁）、限时的并发探测。
**简化版：** 想要"第一个成功才算成功"用 `asyncio.wait(..., FIRST_COMPLETED)` 循环；想要"第一个完成（无论成败）"近似 `asyncio.wait_for` 超时。

## 8. 流式 / 逐项处理（Streaming）
结果是一个序列，边产生边消费，不攒齐。适合数据量大或实时性要求高。
```python
import asyncio

async def produce_stream():
    """异步生成器，逐项产出"""
    for i in range(5):
        await asyncio.sleep(0.2)  # 模拟流式到达
        yield i

async def main():
    async for item in produce_stream():
        # 每来一个就处理一个，不用等全部
        print("got:", item)

asyncio.run(main())
```
**使用场景：** 大文件/大数据集逐块处理、实时数据流（日志尾随、行情、传感器）、SSE/WebSocket、gRPC streaming、Kafka 消费。
**好处：** 内存占用恒定（不攒全量），首条结果延迟低。

## 9. 可靠投递 / 事务消息（At-least-once, Outbox）
把"要执行的动作"变成"一条消息"发出去，由独立消费者保证执行、重试、幂等。**这是 fire-and-forget 的工程化升级版**——同样不阻塞调用方，但保证最终执行，可观测、可重试。
```python
"""
Outbox 模式示意：业务写库时，同事务把"待发消息"写进 outbox 表；
一个后台 worker 轮询 outbox，投递到 MQ 后标记已发。
消费者消费消息时执行真正的副作用，失败重试，消费幂等。
"""
import asyncio
import random

# 模拟 outbox 表 + MQ
outbox: list[dict] = []
delivered: list[dict] = []

def business_with_outbox(uid: int):
    # 1. 业务操作（例如扣款），同一事务写入 outbox
    #    db.execute("UPDATE account SET balance = balance - 100 WHERE uid=?", uid)
    #    db.execute("INSERT INTO outbox(...) VALUES (...)")
    outbox.append({"uid": uid, "action": "deduct", "amount": 100})
    # 调用方到此就返回了，不等待"扣款结果通知"真正发出

async def outbox_worker():
    while True:
        while outbox:
            msg = outbox.pop(0)
            try:
                await deliver_to_mq(msg)     # 投递到 MQ
                delivered.append(msg)
            except Exception:
                outbox.insert(0, msg)       # 失败放回，待重试
                await asyncio.sleep(1)
        await asyncio.sleep(0.5)

async def deliver_to_mq(msg):
    if random.random() < 0.3:
        raise RuntimeError("mq temporarily down")
    print("delivered:", msg)

# 消费者侧必须幂等：同一条消息可能被消费多次
async def consumer(msg):
    # 用 msg 唯一 id 做去重表，已处理过就跳过
    apply_deduction(msg)

def apply_deduction(msg):
    print("applied:", msg)

async def main():
    business_with_outbox(42)           # 业务立即返回
    worker = asyncio.create_task(outbox_worker())
    await asyncio.sleep(3)
    worker.cancel()

asyncio.run(main())
```
**使用场景：** 操作必须可靠执行的场景——扣款、库存扣减、订单状态变更、跨服务一致性。任何"失败了不能丢、需要补偿或重试"的副作用都该走这条路。
**关键点：** 1) 业务数据与消息同事务写入（Outbox），避免"业务成功消息丢"或"消息发了业务回滚"；2) 消费者必须幂等（同一条消息可能投递多次）；3) 失败有重试 + 死信队列兜底。
---
## 怎么选
回到那个核心问题：**这个调用的结果，调用方需要负责吗？**
- **不需要** → fire-and-forget（丢了无所谓）/ 可靠投递（丢了不行）
- **需要，但能晚点要** → Future / 回调
- **现在就要** → await / gather / 竞速
- **结果是连续不断的** → 流式
- **必须可靠执行** → 事务消息 / Outbox（fire-and-forget 的可靠版本）
从同步阻塞到 fire-and-forget，本质就是在**延迟**和**结果可控性/可靠性**之间权衡。fire-and-forget 换来了最低延迟，代价是放弃了对结果的所有权——所以它只适合"丢了也无所谓"的场景，而真正不能丢的操作必须升级到可靠投递。
