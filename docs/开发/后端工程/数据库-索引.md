# 数据库-索引
下面全程用一本**新华字典**和一张**员工表**来讲，讲完你能直接复述。
---
## 一、索引到底是什么
**场景**：一本 2000 页的字典，没有任何目录，你要找「锟」字。
只能从第 1 页一页页翻 —— 这就是**全表扫描**（`type: ALL`）。
于是字典前面加了「拼音检字表」：按 a、b、c…排好序，你查 kūn，直接定位到第 1832 页。
> **一句话**：索引就是一份「额外维护的、排好序的目录」，用空间换时间。
**代价**：
- 字典变厚了（**占磁盘空间**）
- 每新增一个字，目录也得跟着改（**增删改变慢**）
所以索引不是越多越好 —— 一本字典有 3 个目录还行，有 30 个目录，那你每加一个字都要改 30 处。
---
## 二、为什么用 B+ 树
这是最容易背错的地方，用「找人」来讲。
### ❌ 二叉树：太瘦太高
想象一个公司只有「一个人管两个人」的架构，100 万员工要多少层？大约 20 层。
**每下一层就是一次磁盘 IO**，找个人要问 20 次人，太慢了。
> 磁盘 IO 是毫秒级，内存是纳秒级，差 10 万倍。**树的高度 = IO 次数**，所以核心目标是：**把树压矮**。
### ✅ 怎么压矮：让一个节点管更多孩子
改成「一个人管 1000 个人」的架构，100 万员工只要 2 层。这就是 B 树/B+ 树的思路 —— **矮胖**。
MySQL 读磁盘一次读一页 = 16KB。一个索引项大概 14 字节（8 字节主键 + 6 字节指针），所以**一页能放约 1170 个指针**。
- 1 层：1170
- 2 层：1170 × 1170 ≈ 137 万
- 3 层：1170 × 1170 × 16（叶子每页放 16 行数据）≈ **2200 万行**
> **记这句**："三层 B+ 树能存两千万行，也就是说查任何一行最多 3 次 IO，而且根节点常驻内存，实际只要 2 次。"
### ❌ B 树 vs ✅ B+ 树：差在哪
**B 树**像一本**每一页目录上都顺便印了正文**的字典 —— 目录页被正文挤占，一页放不下几个索引项，树就又变高了。
**B+ 树**的两个改动：
1. **只有最后一层（叶子）存数据**，上面全是纯索引 → 一页能塞 1000+ 个指针，树矮。
2. **叶子节点之间用双向链表串起来** → 这是关键。
链表这个设计解决了什么？
> 查 `where age between 20 and 30`。
B 树：找到 20，然后得回到上层再往下找 21，再回上层找 22…… 来回蹦跶（中序遍历）。
B+ 树：找到 20 之后，**沿着链表一路往右撸到 30 就完事了**。
所以 **B+ 树天生适合范围查询、排序、分页**，而这正是 SQL 最常干的事。
### ❌ 哈希索引：只会点名，不会排队
哈希像一个**储物柜**：给你张纸条写着"38 号柜"，`where id = 5` 一秒拿到，比 B+ 树还快。
但是：
- `where id > 5`？—— 储物柜号码是乱排的，没法范围查。
- `order by id`？—— 做不到。
- 哈希冲突多了还会退化。
> **一句话总结**：等值查询哈希最快，但现实业务里范围、排序、分组太多了，所以 B+ 树是综合最优解。

## 三、聚簇索引 vs 二级索引 vs 回表
继续用字典，这是**最能体现理解深度**的一块。
假设有张员工表：
```sql
CREATE TABLE emp (
  id    INT PRIMARY KEY,      -- 聚簇索引
  name  VARCHAR(20),
  age   INT,
  salary INT,
  INDEX idx_name (name)       -- 二级索引
);
```
### 聚簇索引 = 字典正文（按拼音排序）
主键索引的叶子节点，**直接存着整行数据**。
就像字典正文本身就是按拼音 a→z 排好的，你按拼音找，翻到那一页，**释义就在眼前**。
> `where id = 100` → 一次就拿到整行。**这是最快的查询方式**。
### 二级索引 = 偏旁部首检字表
`idx_name` 的叶子节点里**不存整行**，只存 `name` 和对应的**主键 id**。
就像部首检字表上写的不是释义，而是「**见第 1832 页**」。
### 回表 = 查完部首表，还得翻到正文那一页
```sql
SELECT * FROM emp WHERE name = '张三';
```
1. 查 `idx_name` 树 → 找到 `('张三', id=100)`
2. 拿着 id=100 **再去查一遍聚簇索引树** → 才拿到 age、salary
**查了两棵树**，这就叫**回表**。
> 面试讲法："二级索引叶子只存主键，所以要回表，相当于查两次树。能不能避免？能 —— 用覆盖索引。"
### 覆盖索引 = 部首表上直接写了你要的答案
```sql
SELECT id, name FROM emp WHERE name = '张三';
```
你要的 `id` 和 `name`，`idx_name` 的叶子节点上**全都有**，不用再翻正文了 —— **一次查询搞定**。
EXPLAIN 里会看到 `Extra: Using index`，看到这个就是赚到了。
> 这就是为什么**强烈不建议 ****`SELECT *`** —— 你本来可以不回表的，多要了两个字段就被迫回表了。
**实战优化**：把常查的字段塞进联合索引里，让它变成覆盖索引。
`INDEX idx_name_age (name, age)` → `SELECT name, age FROM emp WHERE name='张三'` 就不用回表了。
### 顺便回答两个延伸问题
**Q：为什么推荐自增主键？**
> 正文是按主键顺序排的。自增主键 = 每次都往**最后一页追加**，很爽。
如果用 UUID（随机），就像往一本排好序的字典**中间硬插字** —— 那一页满了就得**页分裂**，把半页内容搬到新页，还会留下很多空洞，磁盘碎片化、性能下降。
**Q：没建主键怎么办？**
> MySQL 会找一个**唯一非空索引**当聚簇索引；都没有的话，**偷偷生成一个 6 字节的 rowid** 隐藏列。所以聚簇索引一定存在。

## 四、联合索引与最左前缀
这是**出错率最高**的一块，用**通讯录**来讲。
假设有个联合索引 `(省, 市, 区)`，通讯录是这么排序的：
```plain text
安徽-合肥-蜀山     ← 先按省排
安徽-合肥-包河       省相同再按市排
安徽-芜湖-镜湖       市相同再按区排
浙江-杭州-西湖
浙江-杭州-余杭
浙江-宁波-海曙
```
**关键认知：它是「先按省排好，省内再按市排，市内再按区排」。**
### 能用上索引的情况
| 查询 | 能用吗 | 为什么 |
| --- | --- | --- |
| `省='浙江'` | ✅ 用到省 | 省是全局有序的，能二分 |
| `省='浙江' AND 市='杭州'` | ✅ 用到省、市 | 浙江内部，市是有序的 |
| `省='浙江' AND 市='杭州' AND 区='西湖'` | ✅ 全用上 | 完美 |
| `市='杭州'` | ❌ 全表扫 | **"杭州"散落在各处吗？** 不，但你不知道从哪开始找 —— 整本通讯录看"市"这一列是**乱序**的 |
| `区='西湖'` | ❌ 全表扫 | 同上，区更乱 |
| `省='浙江' AND 区='西湖'` | ⚠️ 只用到省 | 浙江段内「区」是乱的（杭州的区、宁波的区混着），只能在浙江范围内逐条过滤 |
> **口述版**："最左前缀就是必须从索引的最左边连续地用。跳过中间某一列，后面的列就用不上了，因为它在那个范围内是无序的。"
### 最容易被追问的：范围查询会「断链」
```sql
WHERE 省='浙江' AND 市>'杭州' AND 区='西湖'
```
**只能用到 省 + 市，「区」用不上。**
为什么？因为 `市>'杭州'` 匹配出来的是**一大段**（杭州之后所有市），这段里面「区」是彻底乱序的 —— 宁波的海曙、温州的鹿城混在一起，没法用索引定位。
> **实战结论（这句最有价值）**：
**建联合索引时，把等值查询的列放前面，范围查询的列放最后。**
比如 `WHERE status=1 AND create_time > '2026-01-01'`，索引要建 `(status, create_time)`，**不能**建 `(create_time, status)`。
### 顺带一个彩蛋
```sql
WHERE 市='杭州' AND 省='浙江'
```
**这个能用上索引！** 因为**优化器会自动调换顺序**。最左前缀说的是「索引列的顺序」，不是「你写 SQL 的顺序」。

## 五、索引失效的典型场景
统一用一个比喻：**只要你对索引列「动了手脚」，排好的序就乱了，目录就废了。**
### 1. 在索引列上做运算或用函数
```sql
-- ❌ 失效
WHERE YEAR(create_time) = 2026
WHERE age + 1 = 20

-- ✅ 改写
WHERE create_time BETWEEN '2026-01-01' AND '2026-12-31'
WHERE age = 19
```
> **讲法**："通讯录是按姓名排序的，你现在要找「名字反过来写等于 XX」的人 —— 原来的排序完全帮不上忙，只能一个个算一遍。"
### 2. 隐式类型转换
```sql
-- phone 是 varchar
WHERE phone = 13800138000    -- ❌ 失效！
WHERE phone = '13800138000'  -- ✅
```
> 为什么失效：MySQL 会把字符串转成数字再比较，等价于 `WHERE CAST(phone AS SIGNED) = 138...`，**相当于在列上用了函数** → 回到第 1 条。
	反过来，`int` 字段传字符串 `WHERE id = '100'` 是**不失效**的，因为是把 `'100'` 转成数字，没动列。
### 3. 左模糊
```sql
WHERE name LIKE '张%'    -- ✅ 能用
WHERE name LIKE '%三'    -- ❌ 失效
WHERE name LIKE '%三%'   -- ❌ 失效
```
> **讲法**："字典按拼音排序，你问『以 zh 开头的字』—— 好查。你问『读音里带 an 的字』—— 对不起，只能全本翻一遍。"
	补充加分：要做全文检索就上 ES，或者如果只查有限字段，MySQL 可能用**索引全扫描**（type: index），比全表扫描略好但仍然慢。
### 4. OR 连接了非索引列
```sql
WHERE name = '张三' OR salary = 5000   -- salary 没索引 → 整体失效
```
> **讲法**："OR 意味着两边都得查全。既然 salary 那边躲不掉全表扫描，那干脆整个都全表扫，索引白建了。"
解法：给 salary 也建索引（可能走 index merge），或者拆成 `UNION`。
### 5. 其他
- `!=`、`NOT IN`、`IS NOT NULL`：**可能**失效 —— 本质是优化器算了一下，发现要扫的行太多（比如超过全表 20%\~30%），**不如直接全表扫**。索引不是必须用，是**优化器觉得划算才用**。
- 联合索引不满足最左前缀（见上一节）。
> **万能收尾**："不过这些都不绝对，MySQL 优化器是基于成本估算的，最终还是得用 `EXPLAIN` 看实际执行计划。"

## 六、一分钟完整口述版（背这段）
> "索引本质是一份排好序的目录，用空间和写性能换读性能。
	MySQL 用 B+ 树，核心诉求是**把树压矮**，因为树的高度就是磁盘 IO 次数。B+ 树只在叶子节点存数据，非叶子全是纯索引，一页 16K 能放一千多个指针，所以三层就能撑两千万行数据。另外叶子节点用双向链表串起来了，范围查询和排序可以直接顺着链表扫，这是 B 树做不到的。哈希索引点查更快但不支持范围和排序，所以不作为默认。
	InnoDB 里主键是聚簇索引，叶子直接存整行；二级索引叶子只存主键值，所以查完还要**回表**去主键树再查一次。避免回表的办法是**覆盖索引** —— 把要查的字段都放进索引里，这也是为什么不建议 `SELECT *`。另外主键推荐自增，随机主键会导致页分裂和碎片。
	联合索引要遵守**最左前缀**，而且**范围查询后面的列用不上索引**，所以建索引时等值列放前面、范围列放最后。
	索引失效主要是在列上做了运算、函数、隐式类型转换，或者左模糊、OR 连非索引列。不过最终以 `EXPLAIN` 为准，重点看 `type` 别出现 ALL，`Extra` 里出现 `Using index` 是最理想的。"
